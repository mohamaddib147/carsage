- `backend/app/supabase_client.py` — shared Supabase client using the service role key (server-side only, bypasses RLS).
- `backend/app/routers/health.py` — `GET /health`, reports API status and DB reachability without leaking error detail.
- `backend/app/auth.py` — `get_current_user_id` FastAPI dependency: verifies the `Authorization: Bearer <jwt>` header against Supabase Auth, since the backend's service-role client bypasses RLS and so must check the caller's identity itself on any user-scoped endpoint.
- `backend/app/routers/trip_planner.py` — `POST /trip-planner/directions`: origin/destination → distance + durations via Google Maps. `GET /trip-planner/fuel-prices`: current price per fuel type in LBP and USD. `POST /trip-planner/estimate`: the full flow — route + the caller's car's fuel_efficiency (km/L) + fuel price (scraped default or manual override) → estimated cost, saved as a new `trips` row. Requires auth; verifies `car_id` belongs to the caller. All return a clear error message, never a stack trace, on failure. **CAR-42**: the response also includes `estimated_cost_current_traffic_lbp/usd` — the same trip with fuel efficiency reduced via `_traffic_adjusted_efficiency` (a capped, documented heuristic: penalty scales with how much slower the traffic-adjusted duration is than the no-traffic baseline, reaching a 30% max at a 2x slowdown). Only the original light-traffic `estimated_cost_lbp` is persisted to `trips.estimated_cost`, unchanged from before CAR-42 — the traffic-adjusted figure is response-only since it changes on every re-check. `/directions` and `/estimate` responses also carry `route_polyline` (CAR-48, response-only, never persisted). CAR-23: origin/destination are trimmed, 1-300 chars (blank/oversized -> 422 before Google is called); car_id must be a UUID; the fuel price override is positive, <=10,000,000 and never NaN/Infinity. CAR-24: authentication is required router-wide (directions and fuel-prices were public).
- `backend/app/routers/car_specs.py` — `GET /cars/spec-suggestions?make=&model=&year=` (CAR-34): best-effort car spec autofill for Car Onboarding. No auth required (public data lookup, not a write); always returns 200 with best-effort/null fields, never errors, so a failed or no-match lookup never blocks onboarding. Response also carries `fuel_tank_capacity_source` (`api_ninjas` | `auto_data` | `ai_estimate` | null). CAR-23: make/model must be non-blank and <=60 chars, year 1900-2100 (else 422 before any lookup). CAR-24: requires a logged-in caller (it was public), declared router-wide.
- `backend/app/routers/ai_advisor.py` — `POST /ai-advisor/classify` (CAR-19, persistence added in CAR-21, YouTube video suggestion added in CAR-40, NHTSA safety grounding added in CAR-36): takes a car issue description + `car_id` (+ optional `conversation_id` to continue a prior conversation), verifies the car and conversation both belong to the caller, saves the user's message, then checks `app.services.nhtsa_safety` — a matching open recall or complaint pattern skips the LLM entirely and forces `mechanic` with an NHTSA-grounded explanation; otherwise classifies via `app.services.llm_client` as before, appending an explicit disclaimer to the guidance if NHTSA doesn't recognize the vehicle at all. Saves the AI's reply (with `recommendation` set), and — only when the recommendation is 'diy' (conserves YouTube quota) — looks up a matching video via `app.services.youtube_client`, updates that same AI message row with it if found, and returns `{conversation_id, recommendation, guidance, video_title, video_url}` (the last two `null` for 'mechanic' or no match). The user's message is saved even if classification then fails. Requires auth. A classification failure returns a clear 503, never a stack trace. Reading past conversation history is a frontend-direct Supabase read (RLS-protected), not a backend endpoint. CAR-22: the description is validated first — real words required (3+ letters, unicode-aware; blank/symbol-only -> 422) and max 1000 characters (-> 422), with clear string messages; the trimmed text is what is saved and used. CAR-22: an unexpected failure looking up or saving the YouTube video never breaks the (already saved) answer. CAR-23: car_id/conversation_id must be UUIDs (malformed -> 422, previously a Postgres 500); the saved reply is capped at 8000 chars to match the DB limit; description limits now live in app/validation.py. CAR-24: authentication declared router-wide. Mentor feedback addition: the classify response also carries `message_id` (the AI reply's own advisor_messages row id), so the frontend can let the user mark a 'diy' reply's `marked_fixed` afterwards without a second lookup.
- `backend/app/services/youtube_client.py` — CAR-40: `search_diy_video(car_context, description)` searches YouTube Data API v3 (`search.list`) for a tutorial matching the car's year/make/model + the issue description, returning the top result's `{video_title, video_url}`. Best-effort only — returns `None` (never raises) if `YOUTUBE_API_KEY` isn't configured, the call fails, the quota is exhausted, or there's no result, so a missing video can never block or break the AI Advisor response. CAR-22: a non-JSON body or an unexpected response shape returns None instead of raising.
- `backend/app/services/nhtsa_safety.py` — CAR-36: `check_safety_data(make, model, year, description)` grounds the AI Advisor's recommendation in NHTSA's official Recalls/Complaints data (`api.nhtsa.gov`, free, no key) — a described issue matching an open recall's Component/Summary, or matching 3+ owner complaints, returns a status the router uses to force `mechanic` and skip the LLM. A vehicle NHTSA vPIC (`vehicle_lookup.lookup_nhtsa`) doesn't recognize at all is reported as `not_found`, distinct from a genuinely clean record — Recalls/Complaints alone can't tell those apart (both return an identical `{Count: 0}` shape), confirmed live. Also confirmed live: both NHTSA endpoints return HTTP 400 (not 200) specifically for a legitimately empty result set, so the body is parsed regardless of status code rather than calling `raise_for_status()`. Every failure mode degrades to `unavailable` (never raises), letting the caller fall back to LLM-only classification. CAR-22 rewrite of the matching: matches on the vehicle SYSTEM (brakes, air bags, steering, ... via NHTSA's component field), not loose words in the free text — safety-critical systems always surface an open recall, others need a shared symptom, complaints need the same system AND shared symptom words. Fixes false "NHTSA recall/complaint" claims that forced 'mechanic' for nearly everything. Model naming fix: when the typed model finds no recalls or complaints, the check asks vPIC for NHTSA's official model name and searches again under it (a 2005 C230 Kompressor has 140 complaints, filed under "C-Class") instead of reporting `not_found`; `not_found` is now only for vehicles vPIC really doesn't know. Cars that already returned data cost no extra requests.
- `backend/app/services/google_maps.py` — isolates the Google Maps Directions API call in one function (`get_route_summary`, CAR-48: was Distance Matrix, which has no route geometry): distance, duration, traffic duration and the encoded overview polyline in a single request; raises `GoogleMapsError` with a safe, user-facing message on any failure. CAR-23: an InvalidURL from httpx becomes the clean maps error, not a 500.
- `backend/app/services/llm_client.py` — CAR-19 AI Advisor classification, isolated behind one function (`classify_issue`) so the provider is swappable: Gemini (`gemini-3.6-flash`) is primary, automatically falling back to Groq (`openai/gpt-oss-120b`) on a 429/5xx/transport failure (live testing found Gemini's free tier frequently returns "503 high demand", so 5xx is treated the same as a rate limit — a genuine 4xx surfaces directly instead). Both providers are prompted for the same JSON shape; a response that can't be confidently parsed defaults to the cautious "mechanic" recommendation rather than ever guessing DIY. Which provider served the response is logged server-side only, never exposed to the client. Note: `gemini-2.0-flash` and `llama-3.3-70b-versatile` (the models named in CLAUDE.md's original spec) have both since been retired by their providers (404s) — swapped for their current free-tier equivalents, confirmed live 2026-09-17. Also `estimate_tank_capacity(make, model, year)` (Car Onboarding tank autofill): asks the same Gemini→Groq chain for a typical tank size in liters, keeps only 5-200 L, returns None (never raises) if unsure/unavailable; shared `_complete` helper. CAR-22: falls back to Groq on ANY Gemini failure (429/5xx, but also 400/401/403/404 config failures like a retired model or bad key, and a 200 with a blocked/empty/non-JSON body); a malformed Groq body gives the clean LLMError, never an unhandled exception. The real cause is logged, never shown.
- `backend/app/services/vehicle_lookup.py` — CAR-34 spec autofill: `lookup_nhtsa` confirms a make/model/year exists via NHTSA vPIC and returns an approximate vehicle type as `engine_type` (vPIC has no free per-model engine spec without a real VIN); `lookup_api_ninjas` queries API Ninjas' Cars API for cylinders, drivetrain, transmission, and (CAR-44, only if the response has one — its docs don't guarantee it, so any key containing "tank" with a positive number is accepted) fuel tank capacity in liters (its MPG fields are paywalled on the free tier, so fuel_efficiency from this source is effectively always null), returning all-null if `API_NINJAS_KEY` isn't set or there's no match; `lookup_fuel_economy` gets official EPA combined MPG from fueleconomy.gov (free, no key) via a 3-step menu walk, converted to km/L; `get_spec_suggestions` combines all three, preferring API Ninjas' fuel_efficiency if ever present and falling back to fueleconomy.gov. Every function is best-effort and never raises. CAR-49: an autofilled tank capacity outside 5-200 L is dropped. `get_spec_suggestions` runs its lookups in parallel and fills the tank capacity from the best source, reported in `fuel_tank_capacity_source`: API Ninjas, else the auto-data.net spec-sheet lookup, else (last resort) an AI estimate. CAR-23: the make is percent-encoded into the NHTSA URL path so it can't change the path/query. Model matching fix: `match_nhtsa_model` finds NHTSA's own name for the typed model (same name, trim like "Camry LE" -> "Camry", or a family like "C230 Kompressor" -> "C-Class" / "328i" -> "3 Series"); `lookup_nhtsa` now also returns that `model_name` (not exposed by `get_spec_suggestions`). Before, only an exact name counted, so a saved Mercedes C230 Kompressor was called unknown to NHTSA.
- `backend/app/services/tank_capacity_lookup.py` — `lookup_tank_capacity(make, model, year)`: reads the real factory fuel tank capacity from auto-data.net (brand → model → generation by year, preferring main generations → trim pages, most common value across a few trims), 5-200 L only, cached in memory (a transient network failure is not cached), never raises.
